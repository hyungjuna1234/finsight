# Architecture Decision Records

## 철학
MVP다. 작동하는 가장 단순한 구현을 고른다. 단, 금융 데이터라서 **싸고 효과가 큰 보안 기본기**(RLS, 서버 전용 비밀키, 로그 비노출, 최소 데이터 전송)는 처음부터 넣는다. 복잡한 장치는 필요가 확인될 때 추가한다. 빼기로 한 것과 이유는 `plan.md` 1-1장에 있다.

---

### ADR-001: Next.js 16 App Router, 쓰기는 Route Handler만
**결정**: 읽기는 Server Component → `server/queries`, 쓰기·AI 호출은 `app/api/**/route.ts` + `handler()` 커널. Server Action은 쓰지 않는다.
**이유**: 자동 실행 에이전트가 따르기 쉬운 단일 규칙. 인증·Origin 검사·검증·에러 변환을 한 곳에서 처리하고, 핸들러를 Vitest로 직접 테스트할 수 있다.
**트레이드오프**: 폼마다 fetch 코드가 조금 늘어난다.

### ADR-002: Supabase(서울) — Auth + Postgres RLS + Storage, 브라우저 client 없음
**결정**: 카카오·구글 로그인은 서버 라우트에서 시작(PKCE), 세션은 httpOnly 쿠키. 사용자 데이터는 RLS로 본인 행만. 권한·무료 크레딧은 `entitlements`로 분리하고 admin만 쓴다. Storage에는 사용자 정책을 두지 않는다.
**이유**: 한 서비스로 인증·DB·파일을 해결하고, 격리를 DB가 보장한다. 브라우저 client가 없으면 XSS가 나도 토큰이 탈취되지 않고 코드도 줄어든다.
**트레이드오프**: 실시간 구독 같은 클라이언트 기능은 쓰지 않는다.

### ADR-003: 카드 이용내역만, 업로드는 한 요청 안에서 동기 처리
**결정**: 은행 파일과 카드 청구서는 감지해 안내만 한다. analyze(최대 60초)와 confirm(최대 120초)을 동기로 처리하고, 실패하면 사용자가 다시 누른다.
**이유**: 은행을 빼면 이체·카드대금 중복 문제와 적요 개인정보 처리가 사라진다. 월 명세서는 수백 행이라 동기로 충분하고, 큐·lease·재시도 워커가 필요 없다.
**트레이드오프**: 매우 큰 파일은 느리다(1만 행 상한). 가계 전체 현금 흐름은 보이지 않는다.

### ADR-004: 열 매핑은 Claude, 파싱은 코드
**결정**: Haiku가 마스킹한 헤더와 샘플 5행으로 열(날짜·가맹점·금액 등)을 매핑하고, 실제 파싱은 결정적 코드가 한다. 확정된 매핑은 헤더 서명으로 **사용자별** 캐시한다.
**이유**: 카드사별 파서를 만들지 않고도 여러 형식을 받는다. 파싱 결과는 재현 가능하고 테스트할 수 있다.
**트레이드오프**: 처음 보는 형식마다 Haiku 호출 1회. 사용자 간 캐시 공유는 오염 위험 때문에 하지 않는다.

### ADR-005: 분류는 사용자 지정 → 이전 거래 → 규칙 → Haiku
**결정**: 같은 가맹점의 사용자 지정·이전 분류를 먼저 쓰고, 키워드 규칙, 마지막으로 Haiku(가맹점명만, 100개씩, enum 검증). 실패하면 `기타`/`pending`으로 두고 다시 분류할 수 있게 한다.
**이유**: 반복 업로드에서 AI 호출이 거의 없어지고, 사용자가 고친 결과가 다음 업로드에 반영된다.
**트레이드오프**: 첫 업로드는 Haiku 의존도가 높다.

### ADR-006: 거래 식별은 승인번호 기반 `identity_key` upsert
**결정**: 승인번호가 있으면 금액을 뺀 키, 없으면 금액·같은 날 순번을 포함한 키. `UNIQUE(user_id, identity_key)`로 upsert.
**이유**: 같은 파일·겹치는 기간을 다시 올려도 중복이 생기지 않고, 해외 결제 추정 금액이 확정되면 같은 거래가 갱신된다.
**트레이드오프**: 기간이 겹치는 업로드 중 하나를 지우면 공유 거래도 빠진다(다른 파일을 다시 올리면 복구).

### ADR-007: Claude 모델 — 매핑·분류 Haiku 4.5, 인사이트·채팅 Sonnet 5
**결정**: 모델 ID는 `services/claude/models.ts`에만 둔다. 인사이트는 숫자 없이 문장만 쓰게 하고 숫자는 서버 집계로 표시한다. 채팅은 비스트리밍, 읽기 전용 도구 2개, 기록은 저장하지 않는다.
**이유**: 싼 모델로 대량 작업, 좋은 모델로 사용자 대면 문장. 숫자 환각과 개인정보 저장 범위를 줄인다.
**트레이드오프**: 1-ingest 이후 fixture로 정확도를 측정하고 필요하면 모델·effort를 바꾼다.

### ADR-008: 결제는 Polar(MoR), `services/billing` 뒤에 격리
**결정**: ₩6,900/월(기본 $4.99). 권한은 웹훅을 트리거로 **Polar Customer State를 다시 읽어** 계산하고, `synced_at` 조건부 업데이트로 순서 역전을 막는다. `requirePro`는 `period_end + 7일`도 확인한다. 4-billing은 Polar 사전 서면 승인 후에만 진행한다.
**이유**: 한국 개인이 세금 처리 없이 해외 결제를 받을 수 있다. 웹훅 이벤트 테이블·재동기화 cron 없이도 중복·유실에 안전하다.
**트레이드오프**: 국내전용 카드는 결제할 수 없다. 이용약관(AUP 19조) 승인 여부가 최대 리스크다. SDK가 alpha라 버전을 고정한다.

### ADR-009: 요금제는 기능으로 구분, 남용 방지는 단순 일일 상한
**결정**: Free = 업로드·분류·월별 대시보드, Pro = 인사이트·채팅·추이·정기결제. 횟수 제한 요금제는 없다. 오늘 행 수를 세는 일일 상한과 Anthropic 콘솔 월 지출 한도로 비용을 막는다.
**이유**: 명세서는 한 달에 한 번 나오므로 횟수 제한은 의미가 없다(창업자 결정).
**트레이드오프**: 동시 요청이 몰리면 상한을 조금 넘을 수 있다.

### ADR-010: 테스트 — Vitest 5 두 환경, PGlite로 RLS, Playwright로 여정
**결정**: `*.test.ts`는 node, `*.test.tsx`는 jsdom. 외부 서비스는 `vi.mock`. RLS는 PGlite에 마이그레이션을 적용해 검증한다. async 페이지는 e2e로 검증한다.
**이유**: 실제 키 없이 harness가 모든 step을 검증할 수 있다.
**트레이드오프**: PGlite가 Supabase와 100% 같지 않다. 안 되면 사람이 `supabase start`로 통합 테스트를 대신한다.

### ADR-011: 개발 보안 — harness 작업 복사본 분리
**결정**: 이 레포에는 운영 자격증명·link·실데이터를 두지 않는다. 운영 작업은 `finsight-ops/` clone에서 사람이 한다. `.env` 접근 차단 hook, 운영 CLI 차단 hook, pre-commit 비밀키 검사를 둔다.
**이유**: harness는 권한 확인 없이 돌고 `git add -A`로 커밋한다. 사고가 나면 되돌릴 수 없다.
**트레이드오프**: 운영 작업 때 복사본을 오가야 한다.

### ADR-012: 카드사 PDF 명세서 지원, 비밀번호는 요청마다 받아 메모리에서만 쓴다
**결정**: `.pdf`를 받는다. `unpdf`(pdf.js 서버리스 빌드)로 글자 조각과 좌표를 뽑고, `pdfTable`이 "날짜로 시작하는 줄 + 오른쪽 정렬 숫자 열"로 표를 만든다. 합계 줄에서 멈춰 아래의 해외이용 상세표를 중복으로 세지 않는다. 열 매핑은 코드가 제안하고(날짜·가맹점·금액으로 읽히는 첫 숫자 열 = 이용금액) Claude에는 보내지 않는다. 암호 PDF는 사용자가 비밀번호를 입력하고, 클라이언트가 그 파일을 처리하는 동안만 메모리에 들고 analyze·confirm body로 보낸다. 서버는 메모리에서 열고 버린다. 비밀번호 오류는 업로드를 실패로 두지 않는다.
**이유**: 카드사가 메일·앱으로 주는 명세서는 PDF가 많고, 엑셀 이용내역을 받기 어려운 사용자(모바일)가 있다. PDF 명세서는 열 제목이 그림인 경우가 있어(NH) 제목 대신 배치로 표를 찾는다. 이용금액을 쓰면 할부도 이용일에 총액으로 잡혀 이용내역 파일과 같은 의미가 되고, 다음 달 명세서의 같은 할부 행은 `identity_key`로 중복 제외된다. 비밀번호를 저장하지 않으므로 유출될 것이 없고, Storage 원본은 암호가 걸린 채로 남는다.
**트레이드오프**: 검증한 실제 PDF는 NH농협카드 1종뿐이다. 다른 카드사 배치는 매핑 확인 화면에서 사람이 고친다. 스캔 PDF(OCR)는 지원하지 않는다(`PDF_NO_TRANSACTIONS`). 한 PDF에 카드가 여러 장이어도 업로드 단위로 카드 하나에 묶인다. 비밀번호 자동 추측(생년월일 대입 등)은 하지 않는다. 새 의존성 `unpdf`(MIT, 하위 의존성 없음)를 추가했다.
